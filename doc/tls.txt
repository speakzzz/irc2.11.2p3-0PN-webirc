Native TLS and CertFP for irc2.11.2p3+0PN
=========================================

ircd can encrypt client connections itself (OpenSSL), without stunnel or
another proxy in front.  Server-to-server links stay unencrypted.

Building
--------

  * Install the OpenSSL development files (Debian/Ubuntu: libssl-dev,
    RHEL/Fedora: openssl-devel).  OpenSSL 1.1.1 or 3.x is recommended.
  * config.h: "#define USE_SSL" (on by default in config.h.dist).  An
    existing build directory keeps its own config.h: add the define there.
  * Re-run ./configure so the build directory gets the new Makefile, then
    "make install".  To build without TLS, #undef USE_SSL and empty
    SSLLIBS in the Makefile.

Certificate
-----------

The server reads, in its configuration directory:

	ircd.crt	certificate followed by the intermediate chain (PEM)
	ircd.key	private key (PEM, unencrypted)

The paths can be changed with TLS_CERT_PATH / TLS_KEY_PATH in the Makefile.
Make the key readable only by the user ircd runs as.

With Let's Encrypt, copy fullchain.pem to ircd.crt and privkey.pem to
ircd.key after each renewal (a deploy hook), then REHASH or send SIGHUP.

  * At startup, if a TLS port is configured and the files cannot be loaded,
    ircd prints the reason and exits.
  * Every REHASH (and SIGHUP) reloads them.  If loading fails, the previous
    certificate stays in use and opers get a "TLS: cannot load" notice in
    &ERRORS.  Existing connections are not affected.

Ports
-----

Mark a P-line with the E flag.  Flags are the sixth field:

	P||||6697||E|

Clients on that port must speak TLS (TLS 1.2 or 1.3).  They are labelled
as secure exactly like the 0PN whoistls 'T' flag (WHOIS numeric 320 and
the connect notice), so 'T' is not needed on E ports.  Keep 'T' only for
ports secured by an external proxy.

On connect, a TLS client also gets:

	*** You are connected using TLSv1.3 TLS_AES_256_GCM_SHA384

Client certificates (CertFP)
----------------------------

The server asks for a client certificate but never requires one, and
accepts self-signed certificates: only the SHA-256 fingerprint is used.
A client that presents one is told its fingerprint on connect:

	*** Your client certificate fingerprint is 4afc45c9...46dbb2

and WHOIS shows it to the user and to operators (local clients only):

	:server 276 <you> <nick> :has client certificate fingerprint <sha256>

Fingerprints can be used in the password field of I-lines and O-lines:

	certfp=<sha256>			certificate must match
	certfp=<sha256>,<password>	certificate and password must match

The fingerprint may be written in upper or lower case, with or without
':' separators (as printed by "openssl x509 -noout -fingerprint -sha256").

O-line examples (with CRYPT_OPER_PASSWORD, the password part is crypted):

	O|*@*|certfp=4afc45c9...46dbb2|alice||10|r|
	O|*@*|certfp=4afc45c9...46dbb2,$1$d21f5c2b$.tr/v.wx...|alice||10|r|

The first accepts OPER alice with any password from a client using that
certificate; the second needs both.

I-line example: give certificate holders their own class, everyone else
falls through to the normal line.  I-lines are checked from the bottom
of the file up, so the certfp line goes last:

	I|*@*||||11||
	I|*@*|certfp=4afc45c9...46dbb2|||10|F|

To get a fingerprint from a certificate file:

	openssl x509 -in client.crt -outform DER | sha256sum

Notes
-----

  * Connection-rate limits (CLONE_CHECK) and flood limits apply to TLS
    clients exactly as to plain ones.
  * A plain-text client connecting to a TLS port is disconnected
    ("TLS error: ...") without affecting anyone else.
  * WEBIRC works on TLS ports as on plain ones.
  * Set TLS_CIPHERS in config.h to restrict TLS 1.2 ciphers; TLS 1.3 uses
    OpenSSL's defaults.  Session tickets and renegotiation are disabled.
